# L4 스위치 (L4 로드밸런서) 정리

## L4 스위치 = L4 로드밸런서

L4 계층의 기술(**Port·IP 기반 스위칭, NAT**)을 사용해 로드밸런싱을 수행하기 때문에 "L4 스위치"라고 불린다. **IP와 포트 번호를 확인해 패킷의 경로를 제어**하는 것이 핵심이다.

## 1. 주요 역할

- **서버 부하 분산 (Server Load Balancer)**: `VIP(Virtual IP)`를 통해 트래픽을 여러 리얼 서버로 분산시켜 안정성을 향상시킨다.
- **헬스 체크 (Health Check)**: 서버의 포트(TCP/HTTP) 상태를 주기적으로 체크해서, 장애 발생 시 해당 서버를 분산 대상에서 제외한다.
- 이 외에도 SSL 오프로드(SSL Offload), 방화벽/VPN 부하 분산(FWLB / VPNLB) 등을 수행한다.

## 2. 분산 방법 (알고리즘)

| 방법 | 동작 |
|------|------|
| IP 해시 | 동일한 사용자는 항상 동일한 서버로 연결 |
| 라운드로빈 | 순차적으로 서버에 분산 |
| 가중 라운드로빈 | 서버마다 가중치를 매겨, 가중치 높은 서버에 우선 배분 |
| 최소 연결 (Least Connections) | 현재 연결 수가 가장 적은 서버로 분산 |

## 3. GSLB (Global Server Load Balancer)

일반 L4 로드밸런서를 넘어, **지리적 위치까지 고려**해서 분산하는 방식이다. (예: 사용자와 가장 가까운 지역의 데이터센터로 연결)

## 참고 — 실무 관점 보충

- **IP 해시**는 "**세션 고정(Sticky Session)**"이라고도 부른다. 로그인 세션을 특정 서버 메모리에 저장하는 구조일 때 유용하지만, 서버 확장·장애 대응이 어려워지는 단점이 있어 세션을 Redis 같은 외부 저장소로 빼는 방식을 더 선호한다.
- **L4 vs L7 로드밸런서**: L4는 IP·포트만 보고 분산해 빠르고, L7은 HTTP 경로·헤더·쿠키까지 보고 분산한다(예: `/api`는 A서버, `/img`는 B서버). Nginx, AWS ALB가 대표적인 L7이다. (아래 4·5장 참고)
- **헬스 체크**는 무중단 배포의 핵심이다. 새 버전을 띄우고 헬스 체크가 통과할 때까지 트래픽을 보내지 않다가, 통과하면 그때 트래픽을 붙이는 식으로 롤링 배포가 이뤄진다.

## 4. 하드웨어냐 소프트웨어냐

로드밸런싱은 "기능(역할)"이고, 그 기능을 **하드웨어 장비로도, 소프트웨어로도** 구현할 수 있다. "L4 **스위치**"라는 이름은 원래 전용 하드웨어 장비를 가리키던 데서 나왔다.

| 형태 | 예시 | 특징 |
|------|------|------|
| 하드웨어 장비 | F5 BIG-IP, Citrix NetScaler, A10 | 전용 칩(ASIC)으로 초고성능, 대신 고가·확장 제약 (금융권·대기업 온프레미스에서 사용) |
| 소프트웨어 (직접 설치) | Nginx, HAProxy, LVS | 저렴·유연, 코드로 자동화 가능 |
| 클라우드 관리형 서비스 | AWS ELB/NLB/ALB, GCP LB, Azure LB | 뒤에서 소프트웨어가 동작하지만 사용자는 서비스로 사용 |

> **웹 개발 관점에서는 소프트웨어(그리고 클라우드 관리형 서비스)라고 보면 된다.** 클라우드 배포 시 NLB(L4)/ALB(L7)를 클릭이나 코드(Terraform 등)로 붙이고, 서버에 직접 구성할 땐 Nginx·HAProxy를, 쿠버네티스에선 `Service`/`Ingress`를 YAML로 다룬다. 물리 장비를 만질 일은 거의 없다.

## 5. Nginx — 웹 서버이자 L7 로드밸런서

Nginx는 한 가지 역할만 하는 도구가 아니라, 설정에 따라 여러 얼굴을 가진다.

- **웹 서버 (정적 파일 서빙)**: HTML·CSS·JS·이미지를 직접 내려준다. 아파치와 같은 영역이며 정적 파일 처리는 오히려 Nginx가 빠른 편이다.
- **리버스 프록시**: 클라이언트 요청을 뒤의 앱 서버(Node.js, Spring, Django 등)로 전달하고 응답을 되돌려주는 중개자.
- **L7 로드밸런서**: 리버스 프록시를 확장해, 뒤에 있는 여러 앱 서버로 요청을 분산한다.

### 로드밸런싱 설정 예시

```nginx
# 뒤에 있는 앱 서버 3대를 그룹으로 묶기
upstream my_app {
    server 10.0.0.1:3000;
    server 10.0.0.2:3000;
    server 10.0.0.3:3000;
    # least_conn;  ← 최소 연결 방식으로 바꾸려면 추가
}

server {
    listen 80;
    location / {
        proxy_pass http://my_app;   # ← 그룹으로 요청을 분산
    }
}
```

`upstream` 블록에 서버를 여러 개 적으면 기본 라운드로빈으로 분산되며, 2장의 분산 알고리즘(라운드로빈·최소 연결·IP 해시)을 여기서 지정할 수 있다.

### L7이라 가능한 경로 기반 라우팅

Nginx는 HTTP의 경로·헤더·쿠키(L7 정보)를 읽을 수 있어, 요청을 내용에 따라 다르게 보낼 수 있다. L4 로드밸런서는 IP·포트만 보므로 이런 라우팅이 불가능하다.

```nginx
location /api/  { proxy_pass http://backend_servers; }   # API는 백엔드로
location /img/  { proxy_pass http://image_servers; }     # 이미지는 이미지 서버로
location /      { root /var/www/html; }                    # 나머지는 정적 파일로
```

### 아파치와의 관계

| 구분 | 아파치(Apache) | Nginx |
|------|---------------|-------|
| 정적 파일 서빙 | O | O (더 빠름) |
| 리버스 프록시 | O (가능하지만 덜 대중적) | O (주력 용도) |
| 로드밸런싱 | O (mod_proxy_balancer) | O (upstream) |

아파치도 로드밸런싱이 가능하지만, 실무에서 리버스 프록시·로드밸런서 하면 압도적으로 Nginx를 많이 쓴다.

> **한 줄 요약**: Nginx = 정적 웹 서버 + 리버스 프록시 + L7 로드밸런서를 한 몸에 가진 도구. 설정 파일에서 어떤 역할로 쓸지 정하는 것뿐이다.
